## Why? Why does it need to be fixed?

Because upstream driver partially works on my board.

A typical DBDC mt7986 board looks like this:
```
+--------------------------------------------------------------+
|                            MT7986                            |
|                                                              |
|   +------------------------------------------------------+   |
|   |                         WED0                         |   |
|   +-----------^------------------------------^-----------+   |
|               |                              |               |
|               v                              v               |
|           +-------+                      +-------+           |
|           | 2.4G  |                      |  5G   |           |
|           +-------+                      +-------+           |
|                                                              |
+--------------------------------------------------------------+
```
and the board I have looks like this:

```
+------------------------------------------------------------------------------+
|                                    MT7986                                    |
|                                                                              |
|   +--------------------------------+    +--------------------------------+   |
|   |              WED0              |    |              WED1              |   |
|   +-------^----------------^-------+    +---------------^----------------+   |
|           |                |                            |                    |
|           |                |                            v                    |
|           |                |                        +-------+                |
|           |                |                        |  5G   |                |
|           |                |                        +-------+                |
|           |                |                                                 |
+-----------|----------------|-------------------------------------------------+
            |                |
    +-------|----------------|-------+
    |       |     MT7916     |       |
    |       v                v       |
    |   +-------+        +-------+   |
    |   | 2.4G  |        |  6G   |   |
    |   +-------+        +-------+   |
    +--------------------------------+
```
Difference:
- Extra mt7916 so it can be sold as tri-band router(AX7800).
- WED1 is used.

With upstream code, WED0 works and 2.4G,6G can be offloaded.

WED1 on the other hand fails to be attached.

## Issues

### 1. Failed to attach WED1
Starts with the log below

```
[   11.150822] mt798x-wmac 18000000.wifi: attaching wed device 1 version 2
[   11.196440] platform 15011000.wed: MTK WED WO Firmware Version: DEV_000000, Build Time: 20240823160852
[   11.205827] platform 15011000.wed: MTK WED WO Chip ID 00 Region 3
[   11.212148] platform 15011000.wed: failed to attach wed device
[   13.219287] platform 15011000.wed: failed to disable wed-wo
```

After adding several lines of `dev_info`, I found the issue.

It fails after `mtk_wed_mcu_load_firmware` and it's quite simple to find out what's wrong after going through the git log.

WO is the part handling RX traffic.

WED1 requires a different mask for WO firmware.

It's a regression introduced adding support for MT7988.
The correct reset mask was removed.

The fix: [link](https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git/commit/?id=9192a18f6de2f5e3eb3813ecd2895ac0f5c008a9)
```
--- a/drivers/net/ethernet/mediatek/mtk_wed_mcu.c
+++ b/drivers/net/ethernet/mediatek/mtk_wed_mcu.c
@@ -367,8 +367,12 @@ mtk_wed_mcu_load_firmware(struct mtk_wed_wo *wo)
 	/* wo firmware reset */
 	wo_w32(MTK_WO_MCU_CFG_LS_WF_MCCR_CLR_ADDR, 0xc00);
 
-	val = wo_r32(MTK_WO_MCU_CFG_LS_WF_MCU_CFG_WM_WA_ADDR) |
-	      MTK_WO_MCU_CFG_LS_WF_WM_WA_WM_CPU_RSTB_MASK;
+	val = wo_r32(MTK_WO_MCU_CFG_LS_WF_MCU_CFG_WM_WA_ADDR);
+
+	if (!mtk_wed_is_v3_or_greater(wo->hw) && wo->hw->index)
+		val |= MTK_WO_MCU_CFG_LS_WF_WM_WA_WA_CPU_RSTB_MASK;
+	else
+		val |= MTK_WO_MCU_CFG_LS_WF_WM_WA_WM_CPU_RSTB_MASK;
 	wo_w32(MTK_WO_MCU_CFG_LS_WF_MCU_CFG_WM_WA_ADDR, val);
 out:
 	release_firmware(fw);
```

Here the bug is that `mt76_wed_init_rx_buf` is hardcoded to use `MT_RXQ_MAIN`.

Band queue mapping:
```
2.4G -> MT_RXQ_MAIN
5G or 6G -> MT_RXQ_BAND1
```
On a non-DBDC mt7986, `MT_RXQ_MAIN` is NULL.

This is fixed by using the correct queue and apply it only for WED v2: [link](https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git/commit/?id=8a177dabeeead47dda4d4f91331282790eed0097)

### 3. Still no traffic

Now with no more panic and error, client can associate but no traffic.

I was out of idea so I went to Claude for help.

Fed it the counters dump before and after a client associate.

It pointed out that `WED_WDMA_RING_TX BASE` and `WDMA_RING_TX(0) BASE` are zeroes and packets tried to go through `WDMA_RING_TX(0)`.

Looking at `mtk_wed_wdma_tx_ring_setup`, `WED_WDMA_RING_TX` only gets configured when `WDMA_RING_TX(0)` is configured and they are actually the same thing.

Packets now flow properply after adding an extra `mtk_wed_wedma_tx_ring_setup` for `WDMA_RING_TX(0)` in `mtk_wed_start`.

The fix is submitted but I am fighting with Sashiko's review. Now it's at v6.

I got a suggestion from Benjamin Larsson and added a debug print in `mtk_flow_set_output_device`:
```
mtk_soc_eth 15100000.ethernet: PPEWDMA br-lan ->
wdma_idx=1 queue=0 bss=0 wcid=1023 amsdu=0
```

Looking at where the queue is set in `mt7915_net_fill_forward_path`, of course another issue caused by assuming every board is DBDC.

```
-	path->mtk_wdma.queue = phy != &dev->phy;
+	path->mtk_wdma.queue = phy->mt76->band_idx;
```
It assumed two phys are set up and not using the default phy means BAND1.

For non-DBDC mt7986, queue will always be 0. We have WED TX offloading now after changing it to rely on band_idx.

This can be verified in PPE0 entries because the flow originiated from LAN which is connected to PPE0.

[Link to the fix](https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git/commit/?id=bade0d238b60c29dafcc7da17501fa489495d6ae)
